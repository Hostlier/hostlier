# Hostlier authorize

Use `hostlier authorize --device ID --on local|HOST --app APP[,APP] --scope deploy --for 2h --max-uses 20`. Include `--secrets NAME[,NAME]` only for existing secret references needed by those apps. An all-access login can issue the grant through a retained approval receipt. Otherwise an owner must independently approve through the controller browser page with a passkey, or add `--key FILE` from their own trusted terminal. Maximum eight hours and 100 uses. This grants arbitrary code deployment for named stateless apps, including access to listed secrets. It excludes persistent volumes, stateful source apps, dependencies, workflows and administrator operations. Do not broaden scope to bypass rejection.

For agents creating several test apps, the owner can grant a sandbox window instead: `hostlier authorize --device ID --on local --app-prefix try- --max-apps 5 [--route-domain try.apps.example.com] [--keep-apps] --scope deploy --for 8h --max-uses 100`. The agent may then deploy new `try-*` apps up to the cap, update the ones its sandbox created, and stop, start, restart or delete them (never purge). Apps the sandbox created are deleted when the window ends unless `--keep-apps` was set. Name test apps with the granted prefix; do not try to adopt existing apps outside it.

For separate permissions, use `hostlier access authorize --device ID --on local|HOST --scope actions --actions apps.deploy,apps.rollback --app APP --for 2h --max-uses 20`. Supported actions are `servers.add`, `servers.remove`, `apps.deploy`, `apps.rollback`, `apps.scale`, `apps.start`, `apps.stop`, `apps.restart`, `apps.remove`, `apps.purge`, `sidecars.remove`, `swarms.view`, and `swarms.manage`. Unknown permissions are rejected.

Server permissions require `--on local` on the master and do not require an app selector. `servers.add` allows `hostlier server approve CODE --server MASTER` without a browser. App actions require exact app names in `default`, or `--swarm NAME` with an optional `--app` restriction, and retain the stateless preparation and secret restrictions. Explicit swarm selection without `--app` covers the whole group. `swarms.view` permits scoped discovery and reads; `swarms.manage` permits group administration without workload mutations or authority to issue grants. Creation and cross-group moves require unbound `swarms.manage` or all access. Group grants bind immutable identity, so deleting and recreating a name never restores old authority. Removing a sidecar needs the base deployment/rollback permission plus `sidecars.remove`; deploying or scaling to zero also needs `apps.stop`; purging an app needs both `apps.remove` and `apps.purge`. Legacy deploy windows cannot substitute for these explicit permissions. Grants cannot be combined to authorize parts of one change, and revocation blocks pending execution.
