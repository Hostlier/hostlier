# Autoscaling research and proposed first scope

Research date: 2026-10-29. This historical research proposed the design and did not itself authorize mutations. The subsequently authorized implementation and its current schema are documented in [Approved native CPU autoscaling](autoscaling.md); the descriptions of then-existing contracts below are historical.

## Existing contracts

`internal/model/model.go` defines `.hostlier` `resources.cpu`, `resources.memory` and optional `replicas` (omission means one; explicit zero is retained). `internal/config/config.go` uses strict YAML known-field decoding. There is currently no autoscaling declaration. The k3s manifest generator (`internal/runtime/k3s.go`) writes CPU/memory **limits**, without explicit requests. Docker admits only zero or one application instance; local persistent volumes prohibit multiple replicas (`internal/runtime/scaling.go`).

`internal/controller/scaling.go` permits scale changes only to CPU, memory and replicas, retaining exact secret revisions. Existing approval previews show aggregate allocation and candidate/source overlap. Zero explicitly promises no automatic wake. Storage replacement requires an exclusive-writer maintenance window. Existing scaling creates replacement revisions; it is not an in-place HPA reconciliation contract.

`internal/model/usage.go` and `internal/runtime/usage_k3s.go` expose read-only aggregate usage, verified owner/application/current-version pod identities, completeness checks and oldest sample timestamp. Unavailable is distinct from measured zero. The current metrics contract aggregates containers and is not a per-container HPA input. CPU capacity is a limit, not an explicit request denominator. `docs/runtime-usage.md` documents the authenticated API.

Durable `ProductPolicy` (`pkg/workflow/product.go`, `internal/controller/product_policy.go`) limits replicas, zero permission and per-container resources and is retained server-side. It constrains mutations; it does not authorize autonomous ones. Existing runtime transition journals, rollback/drain recovery and exclusive controller state ownership (`docs/controller-recovery.md`) must remain authoritative.

## Kubernetes findings

HPA utilization targets depend on resource **requests**; missing relevant container requests prevent that utilization calculation. HPA owns the target Deployment's replica field, so repeatedly applying a fixed replica value fights it. `autoscaling/v2` supports direction-specific rate policies and stabilization; default downscale stabilization is 300 seconds. Resource metrics cannot wake an absent pod. Current upstream zero support requires object/external metrics and version/feature support; manual zero with positive HPA minimum deactivates scaling. Pin behavior to the installed k3s version rather than assuming current upstream features. [Kubernetes HPA documentation](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/).

Requests govern scheduling and CPU allocation under contention; limits constrain consumption. Kubernetes can default a missing request from a limit, absent other admission defaults. Hostlier should explicitly declare and preview requests before promising percent-of-request behavior: relying on admission makes the denominator cluster-dependent. [Kubernetes resource management](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/).

VPA is a separately installed Kubernetes autoscaler project with recommender, updater and admission components, not a free Docker capability. It adds operational ownership for CRDs, compatibility, upgrades, webhook certificates and monitoring. Its upstream repository has release and development material; pin a tested release instead of deploying `master`. [Upstream VPA project](https://github.com/kubernetes/autoscaler/tree/master/vertical-pod-autoscaler).

VPA `Off` produces recommendations; `Initial` changes new pods only; `Recreate` evicts pods; in-place modes depend on supported features and may fall back to recreation. Treat automatic vertical changes as potentially disruptive maintenance. [Kubernetes VPA modes](https://kubernetes.io/docs/concepts/workloads/autoscaling/vertical-pod-autoscale/). Upstream explicitly warns that replacement scheduling is not guaranteed and that HPA/VPA should not control the same resource metric. [VPA limitations](https://github.com/kubernetes/autoscaler/blob/master/vertical-pod-autoscaler/docs/known-limitations.md).

## Recommendation

Start with recommendation-only CPU horizontal scaling for stateless k3s applications, then release autonomous operation only after the delegation and recovery contract below is implemented. Exclude persistent application volumes, databases/resources, independent sidecars/workload groups, vertical resizing, zero/wake, node creation and cloud-provider capacity changes. Keep workload/sidecar design a separate workstream.

Docker vertical sizing can offer an approved recommendation using the existing replacement path, but should not be the first automatic control loop: it may interrupt a single instance and requires spare host capacity. Cloud capacity requires separate provider identities, financial limits, provisioning/drain workflows and failure recovery; an unschedulable pod must never implicitly authorize a VM purchase. Database replication needs engine-specific consistency, promotion and backup semantics and is explicitly outside this scope.

For autonomous v1, prefer a **native `autoscaling/v2` HPA** targeting the active owned k3s Deployment. This reuses Kubernetes metrics handling, tolerance, rate policies and stabilization instead of building and maintaining a second CPU algorithm and durable recommendation history. Hostlier owns the approved policy, HPA lifecycle and revision handoff; HPA alone owns live replicas while delegation is active. Do not run a Hostlier CPU decision loop alongside it. Existing replacement deployments make handoff an explicit integration requirement, but do not inherently block this approach: suspend/delete the old HPA with a durable fenced intent before a manual or revision operation; provision the candidate at the approved initial capacity; transfer delegation only after readiness/cutover and revalidate owner, UID and policy bounds. Repeated manifests must not reset an HPA-owned replica field. A custom Hostlier loop would offer stronger per-sample audit and arbitrary budget enforcement, but duplicates substantial control and restart semantics; reserve it for a demonstrated requirement native HPA cannot satisfy.

## Approval and desired-state ownership proposal

Today every deployment/scale still requires CLI approval. Autonomous mutation conflicts with that rule. A future explicit opt-in could approve a **bounded policy delegation** once, through the existing interactive plan/approval path. This is a product decision and proposed authorization model, not approval granted by this document or the research request. Until accepted and implemented, emit recommendations and require each normal CLI approval.

The approved immutable delegation should bind application/owner, runtime, policy digest/generation, image/template revision, min/max replicas, CPU metric definition, freshness/completeness rules, rate/stabilization bounds, revocation semantics and aggregate capacity ceiling. Effective bounds are the intersection of this delegation and retained ProductPolicy; never broaden the retained policy. Preview peak capacity, current requests/limits, failure behavior and revocation. Store approving identity/time and audit lifecycle changes, approved bounds, observed HPA conditions/events and actual results with operation IDs. Native HPA does not provide a durable transcript of every internal recommendation; do not promise that without additional telemetry. Never include secret values.

A proposed `.hostlier` `autoscaling` block might declare `mode: recommend|delegated`, `minReplicas`, `maxReplicas`, `cpuTargetPercent`, request sizing and behavior settings. These are illustrative future fields and are rejected by today's strict schema. Store live autoscaler decisions separately from the approved project fingerprint/revision: project replica count is the initial/manual intent; delegated effective desired count is a separate durable record; actual ready count remains observation. Ordinary deployments must deliberately suspend delegation, fence the old revision, carry or revoke the policy in their approved plan and transfer ownership after readiness. No background editing of the user's `.hostlier` file.

Manual scale/stop/rollback/revoke takes precedence: acquire the same application mutation lock, advance a fencing generation and durably pause delegation before changing capacity. Explicit zero remains stopped across restarts and cannot be automatically woken. Resumption requires explicit approval against current revision and retained policy. Foreign replica changes are drift requiring a pause and visible explanation, not silent adoption or an endless corrective fight.

## Proposed conservative controller behavior

Use CPU only, explicit requests and minReplicas >= 1. Example reviewable HPA settings: target 65%, cluster-supported tolerance, at most +1 replica per 60 seconds, at most -1 per 300 seconds and 300-second downscale stabilization. These are proposed settings, not claims about Kubernetes defaults. Express behavior with native HPA fields supported by the pinned k3s version, rather than promising a custom consecutive-sample algorithm. Derive maxReplicas from both retained policy and aggregate allocation budget using fixed approved requests/limits; reserve separate headroom for temporary deployment overlap. Expose HPA conditions and lastScaleTime alongside actual desired/ready counts.

Do not interpret the existing usage API's unavailable result as idle or feed its aggregate into HPA. Native HPA should consume the cluster metrics API directly and use its documented missing-metric/readiness behavior; Hostlier usage remains observation. Gate activation on healthy metrics infrastructure and explicit requests, verify full owner/application/revision identity of the HPA target, and pause delegation on ownership/target drift or a prolonged metrics outage. Native HPA may conservatively scale up with incomplete metrics, so do not promise a blanket complete-sample freeze without a separate guard. A stricter freshness/completeness contract requires explicit additional design and tests rather than an assumed native guarantee.

Serialize HPA lifecycle changes with deployment/scale/rollback/delete and drain recovery under the existing state owner plus an application operation lock. Write lifecycle intent and fencing generation before mutation; verify expected Deployment UID/resourceVersion and policy/revision. On restart reconcile owned HPA/Deployment state, pending transfer and drain before enabling any new delegation. Kubernetes HPA continues while Hostlier is down, so a local paused boolean or approval expiry is insufficient: pausing must durably remove or disable the HPA before a conflicting action. Do not advertise automatically enforced expiry until an independent in-cluster expiry/revocation mechanism exists; otherwise require explicit revocation and disclose persistence. HPA controller restart may lose in-memory stabilization history: use conservative supported behavior settings and test that case rather than claiming durable history. Recovery at a new location must honor existing activation fences. No multi-controller Hostlier writer assumption.

If an upscale is unschedulable, keep existing healthy serving capacity, report pending/capacity exhaustion, back off and cap attempts. Do not reduce resources, remove healthy pods, grow nodes or deploy a different image to satisfy the recommendation. Memory pressure/OOM is surfaced for manual resource review rather than interpreted as permission for automatic vertical resizing.

## Required local real E2E evidence before enabling delegation

Use a disposable Linux k3s VM, pinned cluster/metrics-server versions, fixed resource requests/limits and a tiny HTTP fixture that reports its pod identity and has an explicitly enabled CPU-burn endpoint. Keep an authenticated Redis marker as a dependency/data integrity witness, not as an autoscaling target. Poll actual Kubernetes Deployment/pod state and certificate-valid application HTTPS; Hostlier or HPA events alone cannot prove scaling.

1. Run a test-only scoped Metrics API fixture feeding deterministic timestamped per-pod samples to the real native HPA controller in an isolated cluster; prove 1 -> 2 -> capped maximum -> stabilized 1, exact rate bounds and no oscillation. Include genuine zero, stale, missing pod/container, malformed, duplicate, foreign-owner and old-revision samples. This proves decisions against a real runtime, not genuine CPU observation.
2. Independently use real metrics-server plus sustained bounded CPU load to prove the complete collection -> decision -> scheduled pod -> routed HTTPS chain. Assert bounded eventual outcomes, not exact sample times or CPU decimals. Remove load, wait the configured downscale window and verify continued service and Redis data.
3. Kill Hostlier after durable HPA lifecycle intent, during HPA deletion and target transfer; restart and prove reconciliation, no competing replica writer and no leaked revision. Restart the native HPA controller too and measure stabilization behavior. Test revocation and manual scale/stop/rollback racing an HPA update, including zero across controller and VM restart. Verify Hostlier downtime leaves a valid delegation bounded by its installed HPA, and that pause really removes/disables the HPA.
4. Exhaust allocatable CPU in the disposable VM. Prove the attempted replica stays pending, original HTTPS survives, retry is bounded and no node/cloud/database mutation occurs. Restore capacity and verify controlled convergence.
5. Approve a new application revision while autoscaling is active; inject delayed old-revision samples and prove no old Deployment scales after cutover. Test rollback pauses delegation and restores reviewed manual capacity. Inspect actual labels, requests, limits, desired/ready counts, journal and audit records.
6. Prove no delegation means no mutation, and rejection occurs before runtime mutation for Docker, volume-backed apps, requests absent, unsupported metrics, max above retained ProductPolicy, unauthorized policy edits and any zero minimum. Keep the existing installed CLI approval/decline/interruption and scale rollback gates passing.

These tests are proposed acceptance gates and have not been executed as part of this documentation work.
